# 設計方針

機能を足したり UI を変えたりするときに前提とする方針です。
「なぜそうしないのか」を残しておき、同じ議論を繰り返さないためのメモです。

## 原画の作業には対応しない

PaintMaskAnimator は **動画以降の工程**（動画・仕上げ）を行うツールとして設計します。
原画の作業（原画番号の管理、原画から動画への番号の振り直しなど）はこのツールの対象にしません。

**理由**

- 原画と動画では、セル番号の体系がまるごと置き換わります。原画は原画ごとの番号に
  中割り指定（「・」、ア・イ・ウ、逆シート指定など）が付き、動画になると通し番号に
  振り直されます。
- 両方の工程を 1 つのツールで扱うと、番号の付け方・並べ替え・逆シートの扱いが
  すべて二重になり、作業の流れもデータ構造も大幅に複雑になります。

**このため**

- 原画やタイムシートの中割り指定は、外部から受け取る **参照用の情報** として扱います。
  編集の対象にはしません。
- セル番号は動画番号だけを持ちます。原画番号から動画番号へ振り直す仕組みは作りません。

## セル番号は整数の連番だけにする

セル（絵）の番号は **1 から始まる整数** だけを認めます。
`1.5` のような小数や、`ア`・`イ` のようなカナ、`2'` のような記号付きの番号は使いません。

**理由**

- After Effects などの読み込み先では、整数以外の番号を正しく扱えません。
- 連番タイムライン（連番モード）は、番号が整数で順に並んでいることを前提にしています。

**このため**

- 既存のキーフレームの間に新しい絵を足した場合でも、整数の番号を付けます。
- 番号の順番とタイムライン上の登場順がずれたときは、「番号の正規化」
  （タイムラインの順番で振り直す）で揃えます。
- 新しく足した絵には、既存の番号を変えずに済むよう **末尾の番号**（最大の番号＋1）を付けます。
  後ろの番号を繰り下げる方式は採りません。

データの本体を連番にし、タイムラインを表として扱う設計は
[sequence-first-data-model.md](sequence-first-data-model.md) に記録します。

### 撮影済みのカットでは正規化しない

撮影済みのカットをリテイクで直し、中割りを足す場合は、番号の正規化をしてはいけません。
足した絵は末尾の番号のままにします。

**理由**

- AE ではすでにタイムリマップを打っています。足したところ以外の番号が変わると、
  同じ番号が別の絵を指すようになり、撮影データと食い違います。
- たとえば A4 が表す絵は、リテイクの前後で同じでなければなりません。

正規化の確認画面には、この注意を必ず表示します。

## 将来は Rust へ置き換えていく

PaintMaskAnimator は、将来的に Rust へ置き換えていく方針です。
ただし一度に全部を書き直すのではなく、**重い計算から少しずつ** Rust の部品にします。

最終的には画面を含む全体の Rust 移行を目指します。移行中は既存の操作を維持し、
独立した計算部品、状態管理、画面の順に進めます。

Rust の部品は、Python・Qt に依存しないクレート **`pma-core`**（`native/core`）に
まとめます。`native/`（`pma_native`）は、それを Python から呼ぶための薄い入口だけに
します。`pma-core` は今の PC 版だけでなく、将来の画面（Tauri など）と iPad 版
（[`FORMAT.md`](../FORMAT.md) の Swift + Rust フォーク）が共通で使う中身です。
作業の手順は [#96](https://github.com/SehataKuro/PaintMaskAnimator/issues/96) にまとめています。
シーク・表示切り替えの実装と計測は [display-performance.md](display-performance.md) に記録します。

**理由**

- 重い計算（PNG の読み書き、塗りつぶしの判定、色の集計など）は、Rust にすると
  速くなり、並列にもしやすくなります（Python の GIL の制約がありません）。
- 一方で、画面（Qt・PySide6 とドッキングの Qt Advanced Docking System）を
  一度に作り直すと、数か月は新しい機能を入れられなくなります。Rust から
  Qt Widgets とドッキングをそのまま使う手段もほぼありません。
- 大手のペイント・アニメソフト（Krita・OpenToonz・Photoshop など）も、
  中身はネイティブで、画面は Qt や独自の UI という分け方をしています。
  CLIP STUDIO PAINT・Affinity のように iPad 版を出しているソフトも、中身を共通にして
  画面を OS ごとに作っています。
- 計算とデータがすべて Rust になれば、Python は不要になります。配布物が軽くなり、
  起動が速くなり、PySide6・NumPy・Rust 拡張をまとめて配る手間がなくなります。
- PySide6 は iPad（iOS）で動きません。中身が Rust なら、iPad 版でもそのまま使えます。

**このため**

- Rust にする部品は「画像（配列）を受け取って結果を返す」だけの形にし、
  画面や Qt に触れさせません。画面を Rust へ移すときも、そのまま使えます。
- `pma-core` には `pyo3`・Qt・ファイル操作（`std::fs`）・スレッド・C ライブラリに
  依存するクレートを入れません。`wasm32-unknown-unknown`（Tauri の WebView 内）と
  `aarch64-apple-ios`（iPad）でもビルドできることを CI で確かめます。ファイルを開く・
  並列にする・GIL を手放すのは、呼び出し側（`native/` など）の仕事です。
- CLIP 読み込み（`clipfile` が SQLite を使う）は `pma-core` に入れず、`native/` に残します。
- 新しく重い計算を書くときも、同じ形（画面から切り離した純粋な関数）で書き、
  あとで Rust へ移しやすくしておきます。
- Rust拡張は開発環境・配布版ともに必須とし、移行済み処理にPythonへの
  実行時フォールバックは基本的に設けません。未導入・旧版なら起動時に
  インストール／再ビルドを案内して停止します。`PMA_NO_NATIVE`も廃止します。
  比較検証用のPython実装はテストで明示的に使用します。
- NumPyとの組み合わせが速い処理、型ごとに異なる処理、まだRustへ移していない
  処理は残します。GPUは任意機能のままとし、利用できない場合は必須のRustを
  含むCPU経路で動作します。
- CLIP読み込みは`clipfile-rs`を使い、独自のPythonパーサーは持ちません。
- 置き換える順番は、効果の大きいものからにします。`.pman`・PNG の読み書き、
  塗りつぶしの判定（バケツ・ドラッグ塗り・串刺し塗りの追跡が共通で使う）、
  色の集計・減色、自動塗りなどの残りの重い計算の順を目安にします。
- 計算のあとは、データの本体を Rust へ移します。今は画素の本体が `QImage` なので、
  まず入れ物（`PmaImage`）を挟んで呼び出し元を寄せ、中身を Rust のバッファ
  （書くときに複製する共有）へ差し替えます。Undo と複製が今の `QImage` の
  暗黙共有と同じ軽さであることを、差し替えの条件にします。最後に `Document` と
  Undo を Rust へ移し、変更通知は Qt のシグナルではなく「変わった範囲の一覧」を
  返す形にします（どの画面からでも使えるように）。
- 操作したときの重さ（Undo やコマ移動の一拍）の多くは、タイムラインの表を毎回
  作り直していることが原因で、Rust にしても変わりません。こちらは変わったところ
  だけを更新するように直します。

### 履歴の入れ物は画面を移すまで Python に置く

文書（コマ・列・セル番号・連番保管）の正本は Rust（`pma-core` の `document`）に
移しました。一方、Undo の履歴の入れ物（Undo 列・Redo 列・捨てられた未来の分岐）は
Python のキャンバスのリストのまま残し、判断だけを Rust（`pma_core::document::history`）
で行います。上限での切り詰め件数、分岐点の付け替え、分岐の本数の上限、分岐へ切り替える
ときの手数、ヒストリーパネルの列の割り当てがそれに当たります。

**理由**

- Undo の各件は、PmaImage など画面側の値を持ちます。パレットの状態や変形の途中の点も、
  文書の Undo と同じ列に並びます。入れ物だけ Rust に移すと、これら画面側の値まで
  Rust で持つ必要があります。
- 入れ物ごと Rust に置くと、リストとして振る舞う窓口を作り、それを直接触る画面の
  モジュールやテストまで同じに動かす必要があります。挙動を変えずに移すのが難しく、
  得られるものに見合いません。

**このため**

- `pma-core` には、Undo の各件を型引数で持つ `History<E>` を置き、Python と同じ判断で
  動くことを Rust のテストで確かめています。画面を Rust へ移すときは、これを履歴の本体にします。
- 件数と論理バイトの上限は今どおり Python の設定から、分岐の本数の上限は Python の定数から渡します。

### 画面の方式：Tauri に決めた（2026-11-27）

画面（GUI）は **Tauri**（画面は HTML／JavaScript、中身は Rust）で作ります。
候補だった egui ＋ egui_dock とは、小さな試作で次の4点を比べました
（結果は [`prototypes/README.md`](../prototypes/README.md)）。

- macOS と Windows の両方で、ペンタブレットの筆圧が取れるか
- 1920×1080 のキャンバスで、ブラシの遅れが今と同じか、それより小さいか
- 日本語入力（レイヤー名やスクリプト）が普通に使えるか
- パネルのフロート・ドッキング・タブ分割が、今と同じように使えるか

ブラシ・日本語入力・ドッキング（別の OS の窓に出すことも含む）は、どちらも macOS で
確かめられました。Tauri にしたのは、日本語入力が WebKit の標準のまま使えること、
別の OS の窓に出すのを dockview の機能で賄えること、同じ画面を iPad にも持っていける
見込みがあることからです。

筆圧は、macOS では WKWebView が渡さないので、Rust 側で NSEvent を読んで画面へ送る
部品を作ります。ペンタブレットの実機と Windows（WebView2）での確認はまだです。
これが済み、Tauri の画面で今の操作ができるようになるまでは、配布する画面は Qt のままにします。

同じ画面が iPad でも使えるかは、次を試作で確かめます。

- Apple Pencil の筆圧・傾きが取れ、遅れが作業に支障ないか
- 4K の画像の表示・ズーム・バケツ塗りの反映が十分に速いか
- ファイルアプリから素材のフォルダをまとめて読み込めるか

キャンバスは、画像を GPU のテクスチャとして持って WebGL2 で表示し、
変わった範囲だけを書き戻す形にします（画像全体を毎回 WebView へ送らない）。
操作してすぐ結果を見たい計算は、`pma-core` を WASM にして WebView の中で動かします。

iPad で足りなければ、Apple 向け（Mac・iPad）の画面は SwiftUI＋Metal で作り、
Windows は Tauri のままにします。どちらに決まっても `pma-core` はそのまま使います。
