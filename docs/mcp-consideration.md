# MCP 対応の検討資料

PaintMaskAnimator（PMAn）に MCP（Model Context Protocol）を導入する場合の
選択肢と工数見積もりを比較する。**判断材料の提示のみで、実装方針は未決定。**

作成時点のコードベース: v0.6.4

---

## 1. 前提整理: MCP の 2 つの役割

MCP は「AI クライアント（Claude Desktop / Claude Code など）」と
「ツールを提供するサーバー」の間のプロトコル。PMAn がどちら側に立つかで、
作るものも得られる価値もまったく異なる。

| | A: MCP サーバー | B: MCP クライアント |
|---|---|---|
| PMAn の立場 | 外部の AI に PMAn の操作を**提供する** | PMAn が外部のツールを**利用する** |
| 使う人の動線 | Claude Desktop 等から PMAn のプロジェクトを操作 | PMAn のアプリ内 AI アシスタント |
| LLM 呼び出し | 不要（クライアント側が持つ） | **必要**（API キー・課金・UI を PMAn が抱える） |

---

## 2. 現状コードベースの評価

MCP 化のしやすさを左右する既存の構造。

**追い風**

- `paintmaskanimator/document.py` の `Document` が UI 非依存。フレーム / レイヤー /
  カーソルという「プロジェクトの状態」を Qt ウィジェットなしで保持できる。
- `paintmaskanimator/project_io.py` の `read_project_archive()` /
  `write_project_archive()` が GUI から独立し、`.pma` の入出力を単体で完結できる。
  ここが MCP サーバーのデータ層にそのまま使える。
- `paintmaskanimator/models.py` の `Layer` / `Frame` は dataclass。
  露出（`exposure`）、可視性、不透明度、セル名など、タイムライン編集で意味のある
  属性がすでに構造化されている。
- `optional_deps.py` + `dependency_check.py` に「任意依存は import 失敗を `None` に
  落として機能だけ無効化する」という確立したパターンがある。`mcp` パッケージも
  同じ枠に載せられ、MCP 非導入ユーザーへの影響をゼロにできる。
- テスト基盤が整っている（`tests/test_project_io.py`、`tests/test_document_model.py`
  など）。ヘッドレスな追加機能は既存の作法で検証できる。

**向かい風**

- `Layer.image` が `QImage`。ヘッドレスでも PySide6 への依存は外れない
  （オフスクリーンでは動くが、サーバー用途としては依存が重い）。
- 実際の描画・編集ロジックの大半が `canvas_*.py`（QWidget 側）にある。
  ブラシ、選択、マスク変形などは **現状 Document 経由では呼べない**。
  公開できるのは当面「プロジェクト構造の参照と操作」までで、
  「AI に絵を描かせる」ような用途には届かない。
- 書き出しも `main_window_export.py` の `ExportController` が UI 前提。
  ヘッドレス書き出しには切り出しが要る。
- `constants.CANVAS_WIDTH` / `CANVAS_HEIGHT` などモジュールグローバルへの依存があり、
  1 プロセスで複数プロジェクトを同時に開く設計とは相性が悪い
  （サーバーは 1 セッション 1 プロジェクトに割り切る必要がある）。

## 3. 案 A: PMAn を MCP サーバーにする

`python -m paintmaskanimator.mcp` のような stdio サーバーを追加し、
プロジェクトの参照・編集・書き出しをツールとして公開する。

### 段階分け

**段階 A-1: ヘッドレス `.pma` 操作（GUI に手を入れない）**

`read_project_archive` / `write_project_archive` と `Document` の上に薄いサーバーを乗せる。

| ツール例 | 内容 | 依存する既存コード |
|---|---|---|
| `open_project` | `.pma` を開いてセッションに保持 | `project_io.read_project_archive` |
| `describe_project` | 尺、フレーム数、レイヤー構成、キャンバスサイズ | `Document` / `models` |
| `list_frames` | フレームごとの duration・セル名一覧 | `models.Frame` |
| `get_layer_info` | レイヤーの可視性 / 露出 / 不透明度 / 下書きフラグ | `models.Layer` |
| `set_exposure` / `set_layer_visible` | タイムライン属性の編集 | `models.Layer` |
| `insert_frame` / `delete_frame` / `reorder_layers` | 構造の編集 | `Document` |
| `save_project` | 保存（別名保存を既定にする） | `project_io.write_project_archive` |
| `export_png_sequence` | 連番 PNG 書き出し | 要切り出し（`ExportController` から） |

**段階 A-2: 起動中の GUI に接続**

ローカル IPC（`QLocalServer` など）と `main_window` 側のコマンドディスパッチャを追加し、
「いま編集中のプロジェクト」に対して同じツールを効かせる。undo スタックとの整合、
スレッド境界（Qt のオブジェクトはメインスレッド）の設計が要点。

**段階 A-3: 描画系の公開**

`canvas_*.py` のロジックを UI から切り離すリファクタが前提。これは MCP の話ではなく、
アーキテクチャの話。段階 A-1/A-2 とは独立に価値がある。

### 得られること

- 「30 秒に収まるよう全カットの露出を調整して」「下書きレイヤーだけ非表示にして書き出して」
  といった**尺・構成の一括作業**を自然言語で回せる。
- CI やバッチからの利用（MCP サーバーは CLI としても再利用できる）。
- 外部ツール（スプレッドシートのタイムシート等）との突き合わせを AI 側に任せられる。

### リスク・コスト

- **ファイル書き込みの安全性**：AI がプロジェクトを破壊しうる。既定を「読み取り専用 +
  別名保存」にし、破壊的ツールは明示的なフラグでのみ有効化すべき。
- `PySide6` を持ち込むため、サーバーとしては依存が重い（オフスクリーンプラットフォーム指定が必要）。
- 公開ツールは API 契約になる。増やすのは容易だが、後から消せない。最小から始めるべき。

### 工数見積もり（目安）

| 作業 | 規模 |
|---|---|
| A-1 サーバー骨組み + 読み取り系ツール + テスト | 中（数日規模） |
| A-1 編集・保存系ツール + 安全策 | 中 |
| `ExportController` のヘッドレス切り出し | 中〜大（既存 UI コードのリファクタを伴う） |
| A-2 GUI 接続（IPC・undo 整合） | 大 |
| A-3 描画系 | 特大（前提リファクタが本体） |

## 4. 案 B: PMAn を MCP クライアントにする

アプリ内に AI アシスタントを置き、外部の MCP サーバー（ファイル、参考資料、
制作管理ツールなど）を PMAn 側から呼び出す。

### 得られること

- 「この作品の設定資料を参照しながら作業する」といったアプリ内完結の体験。

### リスク・コスト

- **LLM 呼び出しそのものを PMAn が抱える**：API キー管理、課金、レート制限、
  オフライン時の挙動、プロンプトの UI。MCP は全体のごく一部でしかない。
- MCP クライアント実装 + AI チャット UI + 設定画面が必要で、A-1 の数倍の規模。
- PMAn 単体で完結する価値が薄い。AI アシスタント機能を作る意思決定が先にあり、
  その実装手段として MCP が選ばれる、という順序になる。

### 工数見積もり（目安）

AI アシスタント機能全体として **大〜特大**。MCP 部分だけを切り出す意味は薄い。

---

## 5. 比較まとめ

| 観点 | A: サーバー（段階 A-1） | B: クライアント |
|---|---|---|
| 初期工数 | 中 | 大〜特大 |
| 既存コードへの侵襲 | ほぼなし（新パッケージ追加のみ） | 大（UI・設定・ネットワーク） |
| 必要な新規依存 | `mcp`（任意依存） | `mcp` + LLM SDK + ネットワーク層 |
| ランニングコスト | なし | LLM API 課金 |
| 非利用ユーザーへの影響 | なし（任意依存で無効化） | 設定・UI が増える |
| 中止・撤回のしやすさ | 高い（パッケージ削除で戻る） | 低い |
| 現状の PMAn で出せる価値 | 尺・構成・書き出しの自動化 | 限定的（描画支援には別途 A-3 相当が要る） |

**所見**: 検証コストと撤回可能性の点で、着手するなら A の段階 A-1 が最も割に合う。
B は「PMAn に AI アシスタントを載せるか」という別の意思決定が先で、
MCP 対応の是非として今議論する対象ではない。

---

## 6. 未決事項（判断が必要な点）

1. 想定する利用者は誰か（開発者・パイプライン担当か、一般の作画ユーザーか）。
   前者なら A-1 で足り、後者なら A-2 以降が要る。
2. AI にプロジェクトファイルの**書き込み**を許すか。読み取り専用で始めるか。
3. `mcp` を任意依存にするか（配布ビルドへの同梱可否）。PyInstaller パッケージング
   （`packaging/`）への影響も要確認。
4. A-3 の前提となる `canvas_*.py` の UI 分離を、MCP とは独立の課題として扱うか。
