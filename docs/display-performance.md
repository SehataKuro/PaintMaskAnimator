# シーク・レイヤー表示の高速化と Rust 移行

## 実装

- 編集画面でも、元画像の `QImage.cacheKey()`・表示サイズ・画面のピクセル倍率・
  反転状態に応じた表示用画像を再利用する。元の画素や書き出し解像度は変更しない。
  ストローク中は元画像を描画する。最大96件・64MiB。
- 表示元のキーを各レイヤーで過去へ繰り返し探す代わりに、全コマの索引を作る。
  メタデータ変更、文書置き換え、構造変更の `changed` 通知で更新する。
  再生と編集で同じ計算を使い、明示的な空白キーで露出を止める。
- レイヤーの表示・不透明度の変更では、表示画像とオニオン画像を再利用する。
  オニオンのキーは関係するレイヤーの画素・表示設定を含むので、
  無関係なレイヤーの操作で捨てず、以前の表示状態に戻したときも使える。
  オニオンは最大48件・128MiBのLRU。
- シークバーの同じコマ内での移動は再通知しない。再生ヘッドの移動は
  新旧の列を再描画する。
- Rust の `native/src/display.rs` に露出索引とオニオンの色変換・選択色抽出を移した。
  Qt に依存せず、計算中は GIL を解放する。未導入・旧版の部品、
  `PMA_NO_NATIVE=1` では Python/NumPy に戻る。

## 計測

2026-10-28、Windows x64、Python 3.11、Rust release ビルド。
`python -m scripts.benchmark_display` でウォームアップ後7回の中央値を計測。
画面操作全体の応答時間ではなく、対象処理の比較。

| 対象 | 変更前 | 変更後 |
|---|---:|---:|
| 1,200コマ・8レイヤーの保持区間を64回探索 | 71.917 ms | 1.583 ms |
| 4K画像4レイヤーを960×540へ描画 | 3.274 ms | 0.367 ms |
| フルHDオニオンの色変換 | NumPy 87.988 ms | Rust 13.477 ms |

索引の初回構築は2.228 ms。表示画像の初回縮小、キャッシュを外れた画像、
フィルターやオニオンの初回生成には別途処理が必要。

## 検証

- Pythonの全テストを8ファイルずつ別プロセスで実行し、999件成功・20件スキップ。
  追加した同一コマのシーク通知テストも含む最終確認では、Rust連携・表示・
  タイムラインの80件が成功した。
- Rustの9件のテスト、ruff、pyright、`cargo clippy -- -D warnings` が成功。
- Rust/NumPyの色変換の画素一致、露出・空白キー・欠けたレイヤーの探索結果、
  画素編集時のキャッシュ更新、表示状態を戻したときの再利用を確認。
- 全件を1プロセスで実行するとWindowsのQtウィンドウ破棄中にネイティブクラッシュが
  発生したため分割した。`conftest.py` にも記載されているWindows/QtAdsの
  破棄処理に関する制約があり、一括実行の成功は確認できていない。

## Rust 移行の続き

### 2026-10-29: オニオン有効時のレイヤー表示切り替え

画面表示用のオニオンは、元解像度ではなく表示領域とデバイスのピクセル倍率に
応じた解像度で合成・色変換する。オニオン独自の拡大率とカメラの拡大率も反映し、
元解像度を上限とする。表示サイズをキャッシュキーに含め、ズーム後の画像は
作り直す。全体濃度またはコマ別濃度が0のオニオンは画像生成を省く。
元画像・書き出し・元解像度の合成処理は変更しない。

4K画像4レイヤー、前後2枚のオニオンを960×540で表示する条件で、
新しい表示状態に切り替えた際の合成・色変換を計測した。Rust有効、
Windows x64、Python 3.11、ウォームアップ後7回の中央値。

| 対象 | 元解像度で生成 | 表示解像度で生成 |
|---|---:|---:|
| 表示切り替え＋前後2枚のオニオン再生成 | 236.945 ms | 21.413 ms |

画面操作全体の応答時間ではない。`python -m scripts.benchmark_display`
で再計測できる。表示復帰時のキャッシュ再利用、半透明レイヤー、選択色限定、
アクティブレイヤー限定、2倍のデバイス倍率、オニオン独自の拡大をテストする。

### 2026-10-29: 使用色の表示フィルター

使用色の表示・非表示、単色抽出、子色を親色で表示するプレビューを
`native/src/display.rs` の `filter_palette` に移した。色の集合と置換表を作り、
元画像を1回だけ走査する。置換前の色で判定するため、循環や連鎖のある
置換表でもNumPy版と同じ結果になる。計算中はGILを解放し、Qtには依存しない。
Rust経路では、NumPy版が使う全画素のRGB索引・アルファ判定配列も作らない。
未導入・旧版の拡張と `PMA_NO_NATIVE=1` では従来の処理を使う。

Windows x64、Python 3.11、Rust releaseビルドで、フルHD・100色の画像に
80色の表示指定と64色の置換を適用した。表示結果のキャッシュを毎回外し、
NumPy側の元画像索引は再利用した状態で、ウォームアップ後7回の中央値を計測。
Qtの画像形式変換とPython/Rust間の転送も含む。

| 対象 | NumPy | Rust |
|---|---:|---:|
| フルHDの使用色フィルター・64色置換 | 246.902 ms | 56.220 ms |

`python -m scripts.benchmark_display` で再計測できる。キャッシュに当たる
表示や操作全体の応答時間を示す値ではない。半透明・非表示色・循環置換・
非連続配列・空入力のテストを追加し、NumPyとの画素一致を確認した。

最終的に全体を Rust へ移す方針のもと、今回の表示計算を独立した部品にした。
今後はドキュメントとタイムラインの状態管理を Rust 側へ寄せ、
メタデータの転送も減らす。続いて表示フィルター・合成・画像入出力を移す。
GUI の移行でもこれらの部品を再利用し、筆圧、日本語入力、ドッキング、
Windows/macOS の描画と操作を検証しながら画面を置き換える。

現在のGUIは引き続きQt/PySide6。今回でアプリ全体のRust化が完了したわけではない。
